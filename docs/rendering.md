# Rendering Questionnaire items as HTML

Rendering is any HTML representation that preserves a Questionnaire's observable
semantics. It may be generated by a generic SDC renderer or designed as a bespoke
dynamic interface. The field-name and behavior contracts, rather than the origin
or visual structure of the markup, determine whether it is a rendering of the
Questionnaire.

This is the escape hatch from the finite UI representation available in SDC. The
Questionnaire continues to own questions, types, terminology, constraints and
reactive rules, while HTML is free to use any layout and interaction model that
can honor them and produce the canonical entry list.

## Tree projection

The renderer walks the Questionnaire tree in item order:

- `group` becomes a semantic `<fieldset>` with its children;
- `display` becomes non-interactive content and has no named control;
- every answerable item becomes one labelled control widget;
- child items retain every ancestor in their canonical field path;
- an existing response supplies values but never changes item type or structure.

A non-repeating group still appears in its children's paths:

```html
<input name="item[contact].item[email]">
```

## Compound widgets

One FHIR answer may require several successful controls. Those controls should be
presented as one widget with one label and one focus/hover boundary:

```html
<div role="group" aria-labelledby="weight-label">
  <span id="weight-label">Weight</span>
  <input name="item[weight].value" type="number" step="any">
  <select name="item[weight].unit">...</select>
</div>
```

Visual composition does not change the wire representation. The parser joins
`.value` and `.unit` because they select components of the same item occurrence.

## Repetition

A repeating item or group renders one block per occurrence. Every block carries
its explicit zero-based index in all descendant names. Client-side add/remove
controls may insert trusted server-rendered templates, replacing only the index
token; they do not assemble a QuestionnaireResponse or maintain a second model.

After removing a row, indexes are compacted before submission. Nested repeats use
different tokens at each level, so adding a diagnosis inside visit `2` changes
only the diagnosis occurrence in that visit.

## Enabled, hidden and calculated items

An item disabled by `enableWhen` is hidden and placed in a disabled fieldset. It
therefore contributes neither answers nor browser validation errors. A server
re-render may remove the branch completely.

Calculated and read-only values render as `<output>`, text, or disabled controls.
They are derived again by the server and are never trusted merely because the DOM
marked them readonly. Reactive execution is defined in
[Enablement and calculated fields](expressions.md).

## Layout

Layout has three levels:

1. Defaults follow meaning: short related scalars share a row on wide screens and
   stack on narrow screens.
2. Questionnaire rendering extensions may select tables, columns, option
   orientation, collapsible sections or specialised controls.
3. A genuinely bespoke page owns its markup and uses the same field paths.

Declared Questionnaire layout wins over renderer heuristics. Responsive changes
may rearrange controls but must not rename, duplicate or remove answers.

## DOM markers

Markers help tests, agents and client behavior understand the rendered control;
they are not submitted and are not assertions the server trusts.

| marker | meaning |
|---|---|
| `data-field` | canonical item path represented by the widget |
| `data-type` | Questionnaire item type |
| `data-required` | the item is required when enabled |
| `data-repeat` | container managing repeated occurrences |

The canonical path remains the control `name`. A marker must not become a second
field-address syntax.

## Round trip

Rendering and parsing use the same path constructor. For every editable answer:

```text
parse(render(response)) = response
```

Disabled, calculated and server-owned values are outside the editable subset and
are re-derived from the Questionnaire, stored response or server context.
